# План улучшения certgot

## Цель

Довести утилиту до безопасного и предсказуемого запуска через systemd: исключить запись вне хранилища, корректно сообщать об ошибках, безопасно обновлять сертификаты, ограничить root-контекст, улучшить тесты и документацию.

## Правила выполнения

- Выполнять этапы по порядку. Следующий этап начинать после прохождения тестов текущего.
- Не менять формат существующего YAML без обратной совместимости или явной миграции.
- Не выполнять реальные ACME-запросы в unit-тестах.
- Не смешивать функциональные изменения, рефакторинг и документацию в одном большом коммите.
- После каждого этапа запускать:

```bash
gofmt -w *.go
go test ./...
go vet ./...
git diff --check
```

## Этап 0. Зафиксировать исходное состояние

1. Запустить `go test ./... -cover` и записать исходное покрытие в описание PR. Текущее наблюдаемое значение: около 23.1%.
2. Запустить `go vet ./...`.
3. Убедиться, что рабочее дерево не содержит чужих изменений. Не перезаписывать их.
4. Создать отдельную ветку с префиксом `codex/`.

Критерий готовности: исходный статус тестов и покрытия известен; чужие изменения сохранены.

## Этап 1. Закрыть выход за пределы хранилища

Файлы: `certs.go`, `certs_test.go`.

1. Добавить строгую нормализацию домена в `validateConfig`:
   - убрать пробелы;
   - привести к нижнему регистру;
   - убрать одну завершающую точку, если поддержка FQDN нужна;
   - запретить `/`, `\\`, `..`, абсолютные пути, пустые labels и wildcard во входном `domain`;
   - проверить длину labels и полного DNS-имени;
   - разрешить только корректное базовое DNS-имя. Wildcard приложение добавляет само.
2. Сохранять нормализованное значение обратно в `cfg.Certificates[i].Domain`.
3. Добавить helper безопасного построения каталога сертификата. После `filepath.Abs`/`filepath.Rel` проверить, что итоговый каталог остается внутри `certDir`.
4. Вызывать helper до `MkdirAll`, `chmod`, `chown` и записи файлов.
5. Добавить table-driven тесты минимум для:
   - `example.com`;
   - `EXAMPLE.COM.`;
   - `../../etc`;
   - `/etc`;
   - `example.com/foo`;
   - `*.example.com`;
   - `a..example.com`;
   - слишком длинного label;
   - доменов, различающихся только регистром или завершающей точкой.

Критерий готовности: никакое значение `domain` не может вызвать файловую операцию вне `<storage_path>/certs`; дубликаты выявляются после нормализации.

## Этап 2. Исправить семантику результата процесса

Файлы: `app.go`, `main.go`, `app_test.go` (создать при необходимости), `notify.go`.

1. После обработки всех доменов проверить `results`.
2. Если хотя бы один результат имеет `ResultError`, вернуть агрегированную ошибку после попытки отправить отчет.
3. Не прекращать цикл на первой ошибке: остальные домены должны быть обработаны.
4. Ошибку Telegram считать отдельной:
   - если уведомление обязательное по текущему контракту — вернуть ошибку;
   - если `telegram_url` пустой и уведомление опциональное — явно пропустить отправку без ошибки;
   - зафиксировать выбранную семантику в README.
5. Сохранить ненулевой exit code через существующий `log.Fatalf` в `main`.
6. Добавить тесты: все домены успешны; один домен упал; несколько доменов упали; Telegram выключен; Telegram вернул ошибку.

Критерий готовности: systemd получает failure при любом провале выпуска/сохранения сертификата; отчет содержит результаты всех доменов.

## Этап 3. Безопасно управлять env DNS-провайдеров

Файлы: `certs.go`, `certs_test.go`.

1. Вынести установку env в helper `withEnvironment` или пару `set/restore`.
2. Для каждого ключа запоминать исходное значение и факт его наличия через `os.LookupEnv`.
3. После обработки восстанавливать старое значение; удалять только ранее отсутствовавшие ключи.
4. Не игнорировать ошибки `os.Setenv` и `os.Unsetenv`; возвращать их в `CheckResult`.
5. Не запускать обработку доменов параллельно, пока библиотека получает credentials из глобального environment.
6. Добавить тесты восстановления существующей переменной, удаления новой переменной и ошибки некорректного имени env.

Критерий готовности: обработка одного сертификата не меняет окружение следующего и не повреждает окружение процесса.

## Этап 4. Усилить проверку существующего сертификата

Файлы: `certs.go`, `certs_test.go`.

1. Заменить `checkCertFile` на проверку пары `fullchain.pem` + `privkey.pem`.
2. Проверять:
   - PEM и X.509 корректно парсятся;
   - сертификат уже действует (`NotBefore`);
   - срок больше renewal threshold;
   - SAN содержит базовый домен и `*.domain`;
   - публичный ключ сертификата соответствует приватному ключу.
3. Вынести порог обновления `30` дней в именованную константу или конфигурацию с безопасным default.
4. Различать состояния: отсутствует, поврежден, не соответствует домену, скоро истекает, валиден.
5. Поврежденный/чужой сертификат считать причиной перевыпуска, но отражать причину в логах.
6. Добавить тесты каждого состояния, включая несовпадающий приватный ключ.

Критерий готовности: чужой или несовместимый сертификат никогда не считается валидным только по `NotAfter`.

## Этап 5. Сделать замену cert/key транзакционной

Файлы: `certs.go`, `setup.go` или новый `storage.go`, тесты.

1. Не заменять `fullchain.pem` до успешной подготовки приватного ключа.
2. Записать оба новых файла во временный каталог внутри domain directory.
3. Выполнить `fsync` файлов и каталога, применить permissions/group до публикации.
4. Публиковать согласованную пару через versioned directory + атомарную замену symlink `current`, либо через безопасный rollback при втором `Rename`.
5. Сохранить совместимые конечные пути `fullchain.pem` и `privkey.pem`, если их обещает README.
6. При любой ошибке оставить предыдущую рабочую пару без изменений.
7. Ошибки `chmod`/`chown` сделать фатальными для сохранения, не ограничиваться warning.
8. Добавить fault-injection тесты ошибки записи, chmod/chown и второй стадии публикации.

Критерий готовности: читатель никогда не видит новую цепочку со старым ключом; ошибка доступа не маркируется успехом.

## Этап 6. Защитить ACME account state

Файлы: `certs.go`, `app.go`, тесты.

1. Если `account.key` существует, но не читается или не парсится, возвращать явную ошибку. Не генерировать новый ключ молча.
2. Проверять тип ключа и ошибки `pem.Decode`/`x509.ParseECPrivateKey`.
3. Не загружать старую registration с новым ключом без явной процедуры восстановления.
4. Проверить соответствие email/contact сохраненной регистрации текущему config; как минимум логировать расхождение.
5. Синхронизировать запись account key и registration на диск.
6. Добавить тесты: отсутствующий key; корректный key; поврежденный key; поврежденная registration; несовместимая пара.

Критерий готовности: повреждение account state останавливает запуск с понятной ошибкой и не уничтожает возможность восстановления.

## Этап 7. Исключить параллельные запуски

Файлы: `app.go`, возможно новый `lock.go`, тесты.

1. Создать lock-файл внутри `storage_path`.
2. Захватывать process-level file lock до работы с account/cert state.
3. При занятом lock завершаться с понятной ошибкой и ненулевым exit code.
4. Гарантированно освобождать lock через `defer`.
5. Добавить тест с двумя конкурентными попытками захвата.

Критерий готовности: ручной запуск и systemd timer не могут одновременно менять сертификаты или ACME account.

## Этап 8. Уменьшить привилегии systemd-службы

Файлы: `setup.go`, `setup_test.go`, README.

1. Разделить install-time root и runtime-пользователя.
2. Создать системного пользователя `certgot` без login shell.
3. Передать ему ownership только account state и рабочей части storage.
4. Продумать доставку сертификатов потребителям через группы без запуска всего процесса от root.
5. Добавить в unit минимум:
   - `User=certgot`;
   - `Group=certgot`;
   - `NoNewPrivileges=true`;
   - `PrivateTmp=true`;
   - `ProtectSystem=strict`;
   - `ProtectHome=true`;
   - `ReadWritePaths=/var/lib/certgot`;
   - ограниченный `UMask`;
   - подходящие `RestrictAddressFamilies` после проверки DNS/HTTPS требований.
6. Для `exec` provider выбрать одно:
   - явно отказаться от него в managed systemd mode;
   - разрешать только root-owned executable из отдельного каталога с проверкой владельца/mode;
   - документировать риск и требовать явный opt-in.
7. Добавить golden/unit-тест полного service template.
8. Проверить unit через `systemd-analyze verify` на Linux CI.

Критерий готовности: обычная выдача сертификатов не выполняется от root; service unit проходит проверку systemd.

## Этап 9. Улучшить работу с секретами

Файлы: `types.go`, `certs.go`, `setup.go`, `config-example.yml`, README.

1. Сохранить текущий `env` как совместимый вариант, но добавить ссылки на переменные процесса или отдельный root-readable environment file.
2. Не дублировать секреты при `yaml.Marshal` во время setup без явной необходимости.
3. Запретить вывод секретных значений и полного Telegram URL в ошибки/логи.
4. Добавить helper редактирования token-bearing URL перед логированием.
5. Описать permissions: config и env-файл `0600`, владелец root или runtime user по выбранной модели.
6. Обновить example: отделить секреты от обычных timeout-настроек.

Критерий готовности: рекомендуемый setup не требует хранить все credentials непосредственно в переносимом YAML; логи не раскрывают токены.

## Этап 10. Улучшить setup и CLI

Файлы: `main.go`, `setup.go`, тесты.

1. Заменить `panic` в wizard на обычное возвращение ошибок до `main`.
2. Использовать отдельный `flag.FlagSet`, чтобы CLI было проще тестировать.
3. Проверять ошибки `filepath.Abs`, template parse/execute и JSON marshal.
4. Добавить неинтерактивные flags для автоматизации setup: interval и подтверждение long interval.
5. Сделать installation идемпотентной и описать поведение обновления существующих unit/config.
6. Не перезаписывать существующий config без backup или явного подтверждения.
7. Добавить rollback: при провале после записи unit восстановить прежнее состояние или оставить точную инструкцию восстановления.

Критерий готовности: setup не печатает stack trace, поддерживает automation и не уничтожает рабочую конфигурацию при частичном сбое.

## Этап 11. Исправить модуль и зависимости

Файлы: `go.mod`, `go.sum`, imports при необходимости.

1. Подтвердить целевой module path владельцем проекта.
2. Если репозиторий действительно `github.com/hnnsly/certgot`, заменить `github.com/hnnsly/her-bot`.
3. Выполнить `go mod tidy`.
4. Проверить, почему все зависимости отмечены `// indirect`; прямые imports должны быть direct.
5. Оценить стоимость импорта пакета lego со всеми DNS providers. Не делать самописный fork без измерения.
6. Зафиксировать минимальную поддерживаемую версию Go и проверить ее в CI.

Критерий готовности: module path соответствует репозиторию; `go.mod` отражает реальные direct/indirect зависимости; clean checkout собирается.

## Этап 12. Усилить CI и release

Файл: `.github/workflows/build-release.yml`; при необходимости новый workflow.

1. Добавить CI на `pull_request` и push основной ветки.
2. Отдельные jobs:
   - `go test ./... -race -coverprofile=coverage.out`;
   - `go vet ./...`;
   - `gofmt` check;
   - `go mod tidy` diff check;
   - Linux build;
   - `systemd-analyze verify` для generated units.
3. Release job запускать только после успешного CI.
4. Определить платформенный контракт:
   - оставить Darwin только для ручного run mode и указать отсутствие setup;
   - либо публиковать только Linux, если продукт systemd-only.
5. Pin GitHub Actions по полному commit SHA для лучшей supply-chain воспроизводимости.
6. Сохранять checksums; при возможности добавить подпись артефактов/provenance.

Критерий готовности: PR нельзя слить при падающих тестах/vet/format; release нельзя создать из непроверенного кода.

Критерий готовности: новый оператор может безопасно установить, диагностировать, обновить и удалить certgot без чтения исходников.

## Финальная приемка

Перед завершением агент должен предоставить:

- краткий список сделанных изменений;
- список осознанно отложенных пунктов с причиной;
- вывод `go test ./... -race -cover`;
- вывод `go vet ./...`;
- результат `git diff --check`;
- итоговое покрытие и сравнение с исходными 23.1%;
- результат `systemd-analyze verify` либо объяснение, почему проверка недоступна;
- ручной smoke-test в изолированном временном storage без реального ACME production-запроса;
- подтверждение, что никакие credentials не попали в diff или логи.

Работа не считается завершенной, если исправлены только симптомы, но остаются: path traversal, exit code 0 при ошибке домена, нетранзакционная cert/key пара или root-служба без ограничений.
